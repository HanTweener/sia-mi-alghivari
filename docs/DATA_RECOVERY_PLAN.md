## RTO/RPO and retention targets

D-31 dikonfirmasi pemilik 30 Oktober 2026: backup lokal dan unggah manual Drive setelah sesi demo pada hari yang sama; setiap hari yang mempunyai perubahan bila demo berjalan beberapa hari; backup sebelum migrasi/deployment berisiko yang memerlukan pemulihan data. Retensi normal **3 set lokal terbaru**, **7 backup harian dan 4 mingguan di Google Drive**. Set mingguan dipilih dari harian tanpa unggah duplikat. Syarat pembersihan dan ketertinggalan upload pada bagian D-31 di bawah.

D-32 dikonfirmasi pemilik 30 Oktober 2026: **target formal RPO/RTO tidak diterapkan pada demo portofolio ini**. Usulan angka kehilangan data/waktu pemulihan sebelumnya dibatalkan dari lingkup aktif, bukan keputusan terbuka atau syarat kelulusan rilis demo. Tidak ada janji SLA pemulihan atau layanan24/7.

Jadwal/retensi D-31 dan backup lokal -> Google Drive manual D-30 tetap berlaku. Path/tool/key/kuota serta cara pembuatan arsip belum final. Scope produksi sekolah atau layanan operasional nyata memerlukan penilaian terpisah.

Verifikasi yang tetap diperlukan adalah pemulihan fungsional pada resource uji terisolasi: set dapat diambil/didekripsi, DB dan file cocok, snapshot/audit/histori utuh, aplikasi dapat digunakan dengan grant benar, serta sesi/job lama tidak aktif kembali tanpa rekonsiliasi. Restore belum dijalankan dan tetap NOT RUN; tidak menerapkan target RPO/RTO bukan bukti pemulihan berhasil.

Cut data, asal set dan upload/verification tetap dicatat untuk memilih cadangan yang benar. Perubahan yang diketahui belum ada pada backup harus dijelaskan sebelum restore/cutover data aktif; jangan menyatakan kehilangan nol hanya karena file tersedia. Waktu/durasi boleh dicatat sebagai informasi diagnostik, tanpa pengukuran atau verdict wajib RPO/RTO.

DB dan file memakai recovery set yang sama; waktu cut data, awal/akhir backup dan verifikasi dicatat terpisah. Host mati atau upload tertunda dapat membuat salinan remote tertinggal; jangan menganggap perubahan yang belum masuk backup sudah terlindungi. Belum ada PITR/binlog, replika, failover atau kemampuan mengembalikan setiap detik perubahan yang dijanjikan.

Retensi operasional backup bukan keputusan retensi rapor/audit/domain. Hanya hapus salinan sesuai kebijakan yang disetujui dan sudah ada set pemulihan yang terbukti dapat dibuka; jangan menghapus satu-satunya cadangan yang masih dapat digunakan demi rotasi. Penghapusan pribadi/legal hold dan perlakuan data yang muncul kembali dari backup belum diputuskan; produksi sekolah perlu kajian tersendiri.

App, worker, proses upload/render dan migrator tidak boleh menulis di antara backup DB dan file. Catat titik quiesce dan verifikasi tidak ada penulis lain; mode maintenance UI saja tidak membuktikan seluruh proses berhenti.

Ini koordinasi operasional DB/file, **bukan transaksi ACID lintas filesystem**. Jika writer tidak dapat dihentikan atau perubahan terdeteksi saat capture, set dinyatakan belum konsisten dan tidak diberi label siap restore. Jangan menyalin volume MySQL hidup sebagai cadangan yang diasumsikan valid. Perintah/tool/provider final mengikuti engine yang dipilih; sekarang belum tersedia.

Folder lokal bukan salinan di luar failure domain komputer; registry image bukan pengganti backup data. Folder/akun/kuota aktual, alat enkripsi serta prosedur key recovery belum ditetapkan. Verifikasi dekripsi/integritas dan pengambilan kembali salinan, bukan hanya status upload selesai. Tidak menambah integrasi Drive/OAuth/sinkronisasi otomatis.

Akses backup dapat membuka seluruh data termasuk hash akun dan audit, sehingga terbatas pada operator yang ditetapkan, dengan credential backup/restore sesuai kebutuhan; akun aplikasi/runtime tidak diberi DDL atau UPDATE/DELETE audit. Setup/import memakai akun restore terpisah, pemeriksaan perilaku memakai grant runtime. Key kehilangan/korup atau secret set tidak cocok adalah blocker; jangan membuat APP_KEY baru tiap restart atau memasukkan key ke dokumen/artefak CI untuk memudahkan restore.

Audit akses/operasi backup dicatat sebagai bukti operator minimum yang aman di luar volume sumber, tanpa password, token, dump pribadi atau screenshot data. Infrastruktur backup tidak memunculkan audit/notifikasi domain rekursif. Retensi normal/jadwal dipilih D-31; akses/folder/kuota Drive aktual serta prosedur key recovery masih perlu ditetapkan sebelum aktivasi. Tujuan Drive/manual upload mengikuti D-30; rotasi belum dieksekusi.

## Restore runbook and verification

1. **Tentukan insiden/target dan otorisasi.** Catat environment, host/database/volume/file yang terdampak, set calon, revision/digest, waktu deteksi dan penulisan terakhir yang terbukti. Hentikan promosi CD yang dapat menimpa target; jangan menyamakan restore data dengan rollout image biasa. Pekerjaan pada demo aktif/produksi, penghentian layanan dan cutover membutuhkan instruksi/otorisasi operasional yang sesuai, terpisah dari dokumen ini.
2. **Lindungi sumber dan hentikan efek.** Simpan bukti/log aman serta keadaan rusak bila masih dapat diakses tanpa menambah kerusakan. Hentikan write HTTP, worker, upload/render/migrasi dan akses publik sesuai jendela yang diotorisasi; cegah runner CD aktif bersamaan. Jangan menjalankan fresh/reset/down massal atau menghapus volume lama untuk mencoba pemulihan.
3. **Ambil set dan secret secara terpisah.** Operator berhak memeriksa manifest, integritas/dekripsi, konsistensi timestamp cut DB+file, schema/digest/lockfile/config dan ketersediaan APP_KEY/material yang diperlukan. Salah key, checksum tidak cocok, arsip parsial atau set DB/file beda cut berarti berhenti dan pilih cadangan lain; tidak menebak pasangan file paling baru.
4. **Bangun target pemulihan terisolasi.** Gunakan database/storage/network/project name tersendiri dengan kapasitas cukup; tanpa Tunnel, worker, Reverb broadcast atau outbound effects yang aktif. Egress dibatasi sesuai kebutuhan terotorisasi. Jangan menyalin .env target aktif ke latihan atau menghubungkan aplikasi rehearsal ke DB/demo lama secara tidak sengaja. Restore tidak menjalankan CD/job/migration otomatis dari startup.
5. **Pulihkan versi yang cocok.** Import DB/schema dan file privat ke lokasi terverifikasi memakai akun restore, gunakan image serta konfigurasi kompatibel dan material key yang benar melalui jalur secret aman. Jangan mengasumsikan image terbaru memahami schema lama atau menjalankan migration ke versi baru sebelum baseline restore diverifikasi. Restore volume/data menyeluruh bukan endpoint CRUD pengguna dan bukan izin menulis ulang audit.
6. **Buktikan integritas dan akses.** Cocokkan jumlah/ID sintetis atau manifest aman, FK/unique/status aktif, history assignment, policy global, blank/0, report snapshot/revisi, progression approved/applied dan audit/inbox per operasi. Verifikasi setiap referensi PDF/avatar, checksum/ukuran yang diharapkan, file hilang/korup dan orphan; karantina ketidaksesuaian sebelum cleanup, jangan hapus bukti. Uji login/data/file scope dengan principal runtime, termasuk wali anak lain/guru kelas lain, current policy dan larangan U/D audit/DDL.
7. **Rekonsiliasi kehilangan dan keamanan.** Bandingkan penulisan yang dikonfirmasi setelah cut dengan hasil restore; laporkan yang hilang/tidak dapat dibuktikan. Backup dapat mengembalikan role/relasi/password lama: cocokkan perubahan akses/credential pascasnapshot dengan bukti tepercaya sebelum membuka target. Cabut seluruh sesi/bukti step-up lama melalui mekanisme yang telah diverifikasi, bukan menganggap mengganti APP_KEY atau menghapus row saja menyelesaikan race. Akun/relasi yang belum dapat divalidasi tidak dibuka; recovery identitas/kredensial yang masih Q6 tidak diganti dengan backdoor/reset bebas.
8. **Rekonsiliasi queue dan file tanpa replay buta.** Jobs/failed_jobs dipulihkan sebagai data yang dikarantina sampai versi payload, umur, recipient/current scope dan efek yang sudah commit ditinjau. Jangan menyiarkan hint usang atau mengulang apply/publish untuk membangun inbox. Inbox persisten dapat di-fetch ulang; gap enqueue tidak dibetulkan dengan menjalankan mutasi domain lagi. File final yang hilang tidak diganti diam-diam dengan data operasional baru; pemulihan/render terkontrol memakai snapshot dan lifecycle sah.
9. **Tinjau lalu cutover terpisah.** Setelah pemeriksaan terisolasi lulus dengan bukti nyata dan risiko kehilangan diterima pemilik, minta otorisasi spesifik untuk memilih set, mengalihkan target dan memulai layanan aktif. Pastikan tidak ada write baru ke target lama yang belum direkonsiliasi. Start app dan validasi privat dahulu; worker/Reverb/Tunnel/CD baru diaktifkan terkendali sesuai keputusan operator. Smoke HTTP/DB/file/inbox/current grants dan WSS yang relevan sebelum menyatakan pulih; bila gagal, tahan akses dan pertahankan sumber/target, bukan otomatis menghapus salah satunya.
10. **Catat hasil dan tindak lanjut.** Rekam set/cut, versi/akun/metode, checksum, hasil integritas/akses, job yang ditahan, perubahan yang diketahui belum tercakup dan otorisasi cutover. Waktu/durasi boleh dicatat sebagai diagnostik, tanpa verdict RPO/RTO. Laporan publik hanya metadata teredaksi; hasil gagal tetap dicatat meskipun latihan berikutnya lulus.

**Pemulihan granular:** bila hanya satu file/objek rusak, ekstrak dahulu dari set ke area terisolasi dan bandingkan identitas, versi, hash serta state target sekarang. File cocok dapat dipulihkan lewat prosedur operator yang diotorisasi tanpa menimpa versi final berbeda; koreksi data domain harus melalui action/revisi yang sah dan audit event tambahan. Jangan menyisipkan/menghapus audit agar sejarah tampak mulus, mengimpor sebagian tabel langsung ke data aktif atau mengembalikan approval dari data usang tanpa tinjauan. Jika konsistensi/grant tidak dapat dibuktikan, hentikan pemulihan granular dan rencanakan restore terkoordinasi.

**Batas rollback:** kembali ke image lama hanya aman bila schema/job kompatibel; tidak mengembalikan row/file atau membatalkan MySQL DDL. Restore database juga dapat kehilangan write yang sudah diakui serta mengubah status izin historis. Pilih roll-forward atau recovery set sesuai keadaan aktual, dengan verifikasi dan otorisasi target aktif; tidak menjanjikan one-click rollback atau zero downtime.

## D-30 — arsip lokal lalu unggah manual Google Drive

Dikonfirmasi pemilik 30 Oktober 2026. Host tunggal mempunyai RAM24GB dan SSD2TB dengan ruang kosong100GB; tidak ada perangkat pengganti. Angka CPU generasi13 dilaporkan, model persis belum diverifikasi. Alokasi6GB/4CPU dan kapasitas pengguna belum disepakati/diuji; jadwal/retensi diterima D-31, target formal RPO/RTO dikeluarkan oleh D-32.

Urutan operasional yang dirancang:

1. Periksa ruang kosong host/WSL dan estimasi puncak untuk dump DB, salinan file, arsip, image/build cache serta target restore terisolasi. Ruang100GB adalah fakta saat dilaporkan, bukan kuota khusus backup atau jaminan ruang cukup. Jika tidak cukup, hentikan capture/drill sebelum merusak data; jangan purge volume aktif/cadangan baik secara otomatis.
2. Hentikan writer/DDL pada jendela capture terkontrol sesuai prosedur di atas; ambil DB+file+manifest dengan satu cut konsisten. Enkripsi/validasi arsip di direktori privat operator di luar public webroot, Git dan volume sumber. Penamaan tidak memuat identitas siswa. Alat/path final belum dipilih; pembuatan backup terjadwal/otomatis belum diputuskan.
3. Setelah seluruh bahan set tertutup dari perubahan dan capture berhasil, writer boleh dibuka kembali sesuai otorisasi. Enkripsi/unggah memakai set salinan yang immutable; tidak perlu membekukan aplikasi selama menunggu upload manual.
4. Pemilik mengunggah arsip terenkripsi dan manifest aman yang cocok ke folder Google Drive privat. Tidak ada URL publik/shared-anyone, Drive API/OAuth/credential baru di Laravel, rclone atau sinkronisasi otomatis yang dipilih melalui keputusan ini. Arsip lokal yang belum diunggah dicatat upload_pending pada catatan operator, bukan tabel/status fitur aplikasi baru.
5. Periksa file/set yang tepat, ukuran dan penyelesaian upload; unduh kembali salinan dan cocokkan checksum untuk menyatakan verifikasi integritas remote. Kemampuan dekripsi serta restore diuji terpisah pada lingkungan terisolasi. Download/restore memperhitungkan ruang sementara dan tidak menimpa sumber aktif. Upload sukses saja belum membuktikan recovery set dapat dipulihkan.
6. Catat ID set, cut data, waktu arsip siap, waktu upload selesai, verifikasi remote dan hasil restore secara terpisah. Kunci pembuka/APP_KEY sesuai set memakai jalur recovery aman terpisah, dapat diperoleh ketika host hilang; lokasi/mekanisme itu belum dipilih, nilainya tidak masuk manifest publik atau arsip bersama kuncinya.

Perlindungan ditentukan oleh salinan yang tersedia untuk insiden: rusak data aplikasi dengan disk sehat dapat memakai set lokal terverifikasi; komputer/SSD hilang hanya dapat mengandalkan set Drive yang sudah diunggah/terverifikasi dan key yang dapat dipulihkan. Jangan menyebut arsip lokal sebagai backup offhost atau remote verified sebelum langkahnya dilakukan.

Untuk kehilangan host, gunakan set Drive yang sudah diunggah/terverifikasi serta key yang dapat dipulihkan. Contoh set cutSenin09:00 dan uploadSelasa09:00 tetap berisi data hingga Senin09:00; perubahan setelah cut belum tercakup. D-32 tidak menetapkan batas kehilangan data numerik, tetapi keadaan cadangan dan perubahan yang belum tercakup harus disampaikan apa adanya.

Dengan satu komputer tanpa spare, kerusakan hardware dapat menghentikan demo hingga perangkat diperbaiki/diganti. Tidak menetapkan waktu pemulihan yang dijanjikan. Latihan restore pada host yang masih berfungsi tidak membuktikan kemampuan failover atau pemulihan ketika host hilang.

Retensi normal D-31:3lokal/7harian+4mingguanDrive; kecukupan ukuran arsip/kuota belum diuji. Penghapusan harus mengikuti syarat D-31 dan tidak menghapus satu-satunya set baik. Seluruh capture/upload/download/checksum/dekripsi/restore/rotasi **NOT RUN**; tidak ada akses akun Drive atau tindakan operasional yang dijalankan.

## D-31 — jadwal dan retensi backup manual

Dikonfirmasi pemilik 30 Oktober 2026, melengkapi D-30.

| Keadaan | Tindakan yang disepakati |
| --- | --- |
| Sesi demo selesai | Buat set lokal konsisten dan unggah manual ke Google Drive pada hari yang sama; verifikasi sesuai D-30. |
| Demo berjalan beberapa hari | Backup dan unggah pada setiap hari yang mempunyai perubahan data. Bukan janji backup daemon berjalan saat host mati. |
| Sebelum perubahan berisiko | Buat backup baru sebelum migrasi/deployment yang membutuhkan pemulihan data. Bila membutuhkan offhost baru, tunggu unggah/verifikasi sebelum lanjut sebagaimana gate rilis. |
| Retensi lokal normal | 3 set terbaru yang selesai dibuat/valid, bukan file capture parsial. Tidak otomatis menghapus versi baik ketika set pengganti belum terverifikasi. |
| Retensi Google Drive normal | 7 set harian dari hari aktif terbaru serta4mingguan. Pilih set mingguan dari harian yang valid; satu arsip dapat memenuhi dua label tanpa upload ganda. |

Capture DB+file konsisten/immutable, waktu cut, upload dan remote verification tetap dibedakan. Setelah capture, layanan boleh dilanjutkan tanpa menunggu upload. Bila beberapa set pada hari yang sama, pilih harian dari set valid terbaru berdasarkan cut manifest, bukan waktu upload/mtime; set penting sebelum migrasi dapat dipertahankan sampai perubahan dan recovery yang bergantung padanya dinilai aman. Catatan label harian/mingguan menggunakan konteks kalender saat capture dan tidak diklasifikasi ulang diam-diam saat school_timezone berubah. Jadwal berbasis peristiwa/hari aktif, belum jam tetap, scheduler atau integrasi Drive otomatis.

Pembersihan cadangan lama hanya setelah set pengganti selesai, salinan remote yang diperlukan terverifikasi, serta masih tersedia set yang terbukti dapat dipulihkan. Jangan hapus arsip yang masih dipilih sebagai mingguan karena slot hariannya bergeser; satu file dengan dua label baru eligible dibersihkan ketika kedua kebutuhan retensinya berakhir. Tidak membuat duplikat untuk mengisi7/4 ketika histori belum cukup atau tidak ada perubahan. Jika safety mengharuskan menyimpan lebih dari3lokal sementara, laporkan kebutuhan ruang dan tunda rotasi berisiko; jangan memenuhi kuota dengan menghapus satu-satunya set baik.

Sebelum backup/rotasi, ukur ukuran set, kebutuhan sementara capture/download/restore dan ruang host/WSL aktual. RuangSSD100GB saat dilaporkan dan kuotaDrive yang belum diverifikasi bukan bukti3/7/4 selalu muat. Storage penuh atau unggah tertunda menggagalkan langkah terkait; jangan menandai backup offhost berhasil, menghapus data sumber, atau menurunkan retensi tanpa keputusan pemilik.

D-32 menghapus target formal RPO/RTO dari lingkup portofolio. Jadwal upload manual dan retensi D-31 tetap dijalankan; keterlambatan upload atau perbedaan isi backup tidak boleh disembunyikan. Set lokal yang belum diunggah tidak tersedia jika host hilang. Pemeriksaan restore memastikan data yang memang ada pada set kembali secara konsisten, bukan memenuhi batas waktu/kehilangan data numerik.

Persetujuan ini adalah kebijakan backup demo sintetis, bukan izin menghapus file sekarang atau keputusan retensi domain/audit/rapor/legal hold. Tidak ada purge otomatis, tabel backup aplikasi, layanan cloud baru atau janji24/7 yang ditambahkan. Alat enkripsi/key recovery/path/folder/kuota serta kapasitas masih perlu dibahas/diuji. Target formal RPO/RTO tidak berlaku untuk demo ini (D-32). Semua capture/unggah/rotasi/restore **NOT RUN**.

## D-32 — batas lingkup pemulihan portofolio

Pemilik memilih melewatkan target formal RPO/RTO pada 30 Oktober 2026. Label tidak berlaku hanya untuk target dan gate numeriknya; bukan untuk backup, checksum/dekripsi, rotasi aman, restore DB+file, pemeriksaan histori/current grant atau otorisasi cutover. Tidak ada restore/backup yang dinyatakan PASS melalui keputusan scope ini. D-30/D-31 tetap, seluruh operasi inti NOT RUN. Tidak menambah timer/dashboard/laporan khusus RPO/RTO atau kewajiban menetapkan angka sebelum demo portofolio.
