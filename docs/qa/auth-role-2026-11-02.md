# Authentication and role authorization audit

Date: 2 November 2026 (Asia/Jakarta).
Scope: current working tree, including the owner's uncommitted fixes. No commit, push, deployment, database migration or live notification was performed.

## Risk and acceptance

CRITICAL: authenticated users could read records outside their assignment, retain revoked access, or use obsolete recovery context. Sensitive assets are student/guardian data, staff contact details, grades, attendance, report revisions, audit events and recovery proofs. Entry points include direct URLs, Inertia props, CSV, writes, inbox counts and broadcast authentication.

Acceptance follows `docs/ROLE_PERMISSION_MATRIX.md`, `docs/RESOURCE_ACCESS_POLICY.md`, `docs/AUTHORIZATION_REQUIREMENTS.md` and the existing implementation. Role unions must combine grants for the actual object. A hidden button alone is insufficient. Ambiguous permissions were not expanded.

## Findings repaired

| Area | Former behavior | Current behavior and retained regression evidence |
| --- | --- | --- |
| Account administration | Academic, Data Entry and Principal could open the account-management listing with account metadata. | Account administration is Master-only. `RoleBoundaryTest` exercises read/write denial for all other roles. Existing student guardian-selection flow remains available to authorized operators. |
| Student directory and CSV | Teachers received all students, guardian identities and unrestricted exports. | Teacher list is filtered before pagination to relevant classes, with minimum student fields. Guardian selectors and family columns are withheld. Teacher CSV is denied. |
| Classroom roster/subjects | Read-only pages supplied unrelated student/teacher selectors and full staff models. | Selectors follow management permissions; student/staff projections are minimized. Subject teachers receive assigned subjects. Foreign classrooms remain forbidden. |
| Effective teaching grants | A historical assigned row or a not-yet-started assignment could grant access. Old delegations followed any historical teaching assignment. | Current assignment requires its start date and no end date; grade/attendance delegation uses that current parent. Former/future teachers and old delegations have negative tests. |
| Mixed Data Entry + Teacher | An unrelated teacher role bypassed delegated attendance clear restrictions. Grade entry also restricted legitimate mixed-role teachers by global role. | Rights are evaluated against the actual subject. Delegated operators cannot clear existing rows; actual subject teachers retain their grant. CSV score provenance uses the existing `delegation_id` column. |
| Attendance batch | A foreign enrollment could be silently skipped while other rows committed. | The complete submitted enrollment set is checked before any write. |
| Principal/homeroom | Read and create abilities were coupled; some legitimate readers were denied. | Principal/homeroom read abilities are separate from score/attendance writes, publication and deletion. Negative HTTP tests prove read-only grants do not permit mutations. |
| Enrollment and status | Data Entry could withdraw/transfer enrollments and change student status, including graduation. | Destructive enrollment operations require Master/Academic. Data Entry status changes are denied. Graduation transitions cannot bypass the progression command through biodata editing. |
| Progression proposals | Homeroom assignment gave proposal create/update/delete/submit rights. | Homeroom remains scoped read-only. Master/Academic prepare/apply; Principal approval remains separate, including from Master. Existing progression suites remain green. |
| Learning progress | A current teacher could request an unrelated historical semester or other subjects. | Authorization follows the selected enrollment; terms, subjects and activities are scoped. Legitimate guardian/admin grants combine independently. `TeacherProgressScopeTest` includes historical/transfer/mixed-role cases. |
| Reports | Guardians could use staff URLs to see revision lineage and internal reasons. Academic-only users could edit homeroom notes. Historical report lists were broader than the actual classroom grant. | Staff and guardian projections are separated; report lists are filtered; notes require Master/actual homeroom. Read-only report controls follow server capabilities. |
| Audit | Academic could read user/system events and same-batch records outside academic scope. | A common academic allowlist applies to pagination, individual authorization, related batches and actor filters. |
| Notifications | Old recipient-owned summaries/counts remained available after role/guardian/homeroom revocation; broadcasts carried summaries. | Current resource grants are checked before pagination/count/read actions. Unknown scoped domains fail closed. Broadcasts carry only an ID hint; the client fetches authorized content and clears stale private items. `NotificationRevocationTest` covers revocation and role unions. |
| Sessions | Inactive accounts and obsolete session generations were not enforced on each request. | A fresh active account and matching generation are required, including broadcasting. Setup/pending-choice sessions cannot use domain routes. Existing sessions without the new generation stamp require login again. |
| Recovery | An old browser could finish another password operation's session choice; stale model snapshots could reuse a reset proof. | Browser/operation/flow/credential-version binding and locked atomic proof consumption reject replay. OTP resend and verification serialize on the same user lock. |
| Disable/reactivate | Disabling an account did not permanently invalidate old sessions, guest reset proofs or OTPs. | Both deactivation paths lock the target, advance session/credential generations, clear proof/pending context, revoke OTP and remove sessions in the audit transaction. HTTP tests reject pre-deactivation proof/OTP after reactivation. |
| Authentication abuse | Expired temporary credentials were accepted; login/OTP lacked application throttles and login messages distinguished account state. | Temporary expiry is enforced; account and source limiters protect login/OTP; login uses a common failure message. File limiter supports the current local setup without requiring a missing database cache table. |

The owner's existing frontend changes were preserved. Permission controls were aligned across student, roster, subject, year, grading and report screens. Existing changed source was normalized using the installed formatters; a long existing synthetic PDF string was split without changing its contents.

## Per-role verification

| Role/context | Checked boundary |
| --- | --- |
| Master | Account/settings administration permitted; no Principal approval bypass. |
| Academic | Academic management permitted; account/settings management denied; audit scope restricted; no homeroom-note write without actual homeroom grant. |
| Data Entry | Student operational entry retained; no account/configuration/destructive enrollment/status/publish authority; grade/attendance only through valid delegation. |
| Teacher | Actual classroom/subject/enrollment scope; no foreign class, family directory, configuration or unrestricted CSV. |
| Homeroom assignment | Scoped progress/report grants, read-only progression proposals; no unrelated subject-grade mutation. |
| Principal | Read-only academic operations and exclusive approval/rejection; no account/configuration/grade write/apply grant from Principal alone. |
| Guardian | Own linked child and published/current reports; staff projections and other children denied. |
| Mixed/revoked roles | Object-specific role unions, role-cache refresh, expired/replaced grants, detached children, session invalidation and disable/reactivate recovery contexts. |

## Remaining risks and work outside this audit

- **MEDIUM, open:** OTP recovery may disclose account existence through response timing. Unknown users short-circuit verification while existing users enter the package timebox; synchronous real email delivery could also distinguish issuance timing. Generic messages and throttling do not eliminate this side channel. No timing benchmark or real SMTP test was performed.
- **NOT RUN:** concurrent transactions on MySQL, real email/OTP delivery, an already-connected live WebSocket during revocation, browser CSRF/session-cookie deployment checks, production/remote CI and release gates. SQLite tests do not prove MySQL locking behavior.
- The file limiter is appropriate to the current single-instance setup; shared enforcement is required before multiple app instances.
- Preexisting student Edit has no modal implementation. This is separate functionality debt; authorized admin editing was not built as part of the authorization audit.
- JWT, refresh-token, OAuth and passkey-specific checks are **N/A** to the reviewed local-session implementation.

This report records local implementation/testing and remaining risks. It is not production release approval.
