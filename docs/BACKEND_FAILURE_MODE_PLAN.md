## Test strategy

- Fixture sintetis memisahkan dua kelas/penugasan, wali dengan anak berbeda, role rangkap, delegasi aktif/dicabut dan state draft/published/finalized. Dev/CI/demo memakai resource serta credential terpisah; pengujian failure/load/restore tidak menyasar demo aktif atau Tunnel publik.
- Untuk BF-01/07/08 gunakan engine target dengan akun runtime yang benar; koneksi independen dan penghalang yang terkendali untuk race. Assert baris bisnis, audit tiap objek, inbox per penerima/scope dan status transaksi sebelum/sesudah, bukan hanya HTTP200. Jangan mengganti seluruh DB/policy dengan mock.
- BF-02/05 memeriksa daftar/count/detail/nested ID, bulk, props/file, cache privat dan izin yang dicabut antara buka form dan simpan. Recheck grant pada transaksi sensitif mempunyai urutan commit yang jelas. Error tidak memuat identitas objek terlarang; sesi/izin hilang membersihkan state klien.
- BF-03/06 mematikan/memperlambat worker/Reverb pada lingkungan uji, mengulang job yang sama dan membuka koneksi kembali. Expected: inbox tetap persisten setelah commit, tidak ada broadcast rollback, hint duplikat tidak menggandakan inbox, dan fetch/count mengikuti scope terkini. Dispatch gagal sebelum enqueue tidak dipulihkan oleh retry job yang tidak pernah ada; catch-up adalah pemulihan tampilan.
- BF-04 mengukur jumlah koneksi, lock wait, durasi dan respons error aman pada ukuran beban yang dicatat. Semua operasi yang menunggu harus memiliki batas. Nilai timeout/batch/concurrency/retensi belum ditetapkan; pilih dari pengukuran dan verifikasi sebelum aktivasi, bukan mengarang SLO.
- BF-09 menyuntikkan kegagalan render/write/publish; preview GET tidak membuat file/data. Expected: rapor tetap finalized bila file belum siap, tidak ada tautan sukses palsu; retry berizin memakai snapshot yang sama. Byte yang sudah diunduh sebelum revoke tidak dapat ditarik kembali.
- BF-10 membuat backup dan restore terisolasi dengan manifest revisi/schema/file, lalu memeriksa relasi, snapshot, hash file, akses dan rekonsiliasi job. Teardown hanya menghapus resource uji yang terverifikasi; tidak menyentuh volume dev/demo. Tidak menjalankan restore pada tahap blueprint.

Retry hanya untuk kegagalan transient yang aman diulang, dengan deadline/attempt/backoff terbatas. Mutasi HTTP nonunik yang hasilnya tidak pasti diperiksa melalui GET/list/status berizin sebelum pengguna mencoba lagi; tidak menambah generic Idempotency-Key/receipt table. Version/unique/state dapat menolak replay, bukan janji mengembalikan respons sukses identik.

Kontrak antrean mengikuti [arsitektur notifikasi](NOTIFICATION_ARCHITECTURE.md): timeout worker lebih pendek daripada retry_after; strategi attempts dan batas umur harus benar-benar efektif pada versi framework final. Jangan menganggap tries dan retryUntil otomatis menggabungkan kedua batas. Stub membantu menguji kegagalan deterministik tetapi tidak membuktikan integrasi Reverb/jaringan yang berjalan.

Map BF ke CT/DBV/AZ/SES/AV dan acceptance criteria yang sama pada [CODE_QUALITY_PLAN](CODE_QUALITY_PLAN.md); satu tes yang tepat boleh menjadi bukti beberapa invariant. Tidak membuat suite/abstraksi/layanan baru hanya untuk mengisi tabel ini. Path JUnit, command dan revisi diisi dari konfigurasi nyata setelah implementasi, bukan argv atau artefak rekaan.

- Verification date, command and revision: **NOT RUN**; belum ada command/CI aplikasi inti. Pemeriksaan Markdown dicatat terpisah.
